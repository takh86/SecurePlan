## 1. Normative baseline and contract discipline

The OpenAPI document describes the implemented MVP API, not planned or hypothetical endpoints.

NestJS controllers + explicit Request/Response DTOs are the implementation source used to generate OpenAPI.

Security requirements, RFC 9457 errors, concurrency/idempotency headers and relevant success/error responses must be documented.

The API remains versioned under /api/v1; product release numbers do not automatically create a new API major.

Swagger UI is available in Local; Staging may expose it in a protected manner; Production must not expose a freely public Swagger UI.

The generated OpenAPI artifact remains available to CI/internal tooling even when Swagger UI is disabled in Production.

OpenAPI validity and contract drift are merge/release gates.

| OpenAPI dialect decision D-8.9-01<br>SecurePlan does not manually force a dialect unsupported by the selected NestJS Swagger toolchain. The MVP target is the OpenAPI 3.0.x document generated by the framework/tooling version in use. If the implementation toolchain later produces OpenAPI 3.1.x, that upgrade is allowed only after CI validation and compatibility review; the API semantics defined here do not depend on 3.1-specific features. |

## 3. 8.9.2 - OpenAPI security model

SecurePlan uses server-side cookie sessions. OpenAPI therefore documents cookie authentication as an apiKey-in-cookie security scheme. The exact physical cookie name must come from the same runtime constant/configuration used by the application so documentation cannot drift from deployment.

| components:<br>  securitySchemes:<br>    sessionCookie:<br>      type: apiKey<br>      in: cookie<br>      name: <configured-session-cookie-name> |
| --- |


| Endpoint class | OpenAPI security |
| --- | --- |
| Public: login, activation, password-reset request/reset | security: [] |
| Protected tenant endpoints | security: [{ sessionCookie: [] }] |
| Platform endpoints | Not part of current internship MVP endpoint catalogue; no speculative paths documented. |

### 3.1 CSRF and Origin documentation

CSRF is not modeled as a second authentication identity. It is documented as a required header parameter on protected unsafe requests.

The canonical header is X-CSRF-Token.

POST/PUT/PATCH/DELETE protected cookie-session mutations document the header as required.

GET/HEAD/OPTIONS remain side-effect free and do not require the CSRF header.

Allowed Origin behavior is described in operation/security documentation but is enforced by runtime policy, not client-selected schema values.

| parameters:<br>  XCsrfToken:<br>    name: X-CSRF-Token<br>    in: header<br>    required: true<br>    schema:<br>      type: string |
| --- |


## 4. 8.9.3 - Shared header components

| Header | Direction | Required where | Schema / semantics |
| --- | --- | --- | --- |
| X-CSRF-Token | request | Protected unsafe methods | Opaque session-bound anti-CSRF token. |
| X-CSRF-Token | response | Login and GET /me | Current non-secret CSRF token for frontend use. |
| X-Correlation-ID | response | All API responses | Opaque support/diagnostic correlation identifier. |
| Expected-Version | request | Concurrency-sensitive Duty mutations and APPROVE decisions | Positive integer expected Duty.version. |
| Edit-Lease-Token | request | Interactive plan-entry PATCH/DELETE | Opaque lease-holder token; raw token is not logged. |
| Idempotency-Key | request | Selected critical POST commands | 8..128 visible ASCII; opaque client-generated key. |
| Idempotency-Replayed | response | Idempotent replay where applicable | boolean-like response header indicating replayed logical result. |
| Retry-After | response | 429 and selected in-progress/retryable responses when known | Standard delay/date semantics. |

## 5. 8.9.4 - Schema documentation rules

Every request body uses an explicit Request DTO schema; every success body uses an explicit purpose-specific Response DTO.

Persistence entities are never used directly as OpenAPI response schemas.

Enums are documented with exact case-sensitive wire values.

UUID, date, date-time, month-start and time fields use explicit OpenAPI formats/pattern descriptions matching Phase 8.4.

PATCH DTOs document optional fields and the 'at least one field' application rule in description/validation tests.

Unknown fields are rejected by implementation; examples must not show security-sensitive client fields such as companyId, role or permissions.

Nullable is documented only where API null is explicitly meaningful; omission remains the normal PATCH 'unchanged' signal.

## 6. 8.9.5 - Response documentation policy

| Status | Document when relevant | Canonical meaning |
| --- | --- | --- |
| 200 | Reads, updates/actions returning a representation | Success. |
| 201 | Resource creation | Created resource. |
| 202 | Neutral asynchronous-style password-reset request acknowledgement | Accepted neutral response. |
| 204 | Logout, delete/release operations with no body | Success, no content. |
| 400 | Malformed/validation/query/header contract failures | RFC 9457 problem. |
| 401 | Missing/expired/revoked session or invalid credentials as applicable | RFC 9457 problem. |
| 403 | Visible resource/action forbidden; CSRF/origin rejection | RFC 9457 problem. |
| 404 | Missing or deliberately concealed resource | RFC 9457 RESOURCE_NOT_FOUND. |
| 409 | Business state, uniqueness, concurrency, edit lease, idempotency conflicts | RFC 9457 problem. |
| 429 | Rate limiting | RFC 9457 + Retry-After where known. |
| 500 | Unexpected server error | Sanitized RFC 9457 INTERNAL_ERROR. |

| No HTTP 422 in MVP<br>The OpenAPI contract must not document 422 as the normal SecurePlan validation class. Invalid input remains 400; valid requests that conflict with current business/concurrency state remain 409. |

## 9. 8.9.8 - NestJS Swagger implementation mapping

The exact decorator names depend on the installed @nestjs/swagger version, but the implementation must satisfy the following responsibilities.

| Concern | Implementation responsibility |
| --- | --- |
| Controller grouping | Tag controllers by API area. |
| Operation identity | Explicit summary/description + stable operationId. |
| Request body | DTO class with validation metadata and Swagger schema metadata where reflection is insufficient. |
| Responses | Document success DTO plus relevant RFC 9457 error responses. |
| Cookie auth | Register one sessionCookie security scheme and apply it only to protected operations. |
| Headers | Reusable decorators/components for CSRF, idempotency, expected version and edit lease. |
| Query params | Explicitly document defaults, limits, enums and per-endpoint sort whitelists. |
| Examples | Keep synthetic examples close to DTO/response documentation; no secrets. |
| Hidden internals | Repositories, persistence entities, password hashes, token hashes and internal-only endpoints are not public schemas. |

| API Design<br>  -> Controller + DTO implementation<br>  -> SwaggerModule.createDocument(...)<br>  -> generated openapi.json<br>  -> OpenAPI validation/lint<br>  -> snapshot/diff policy<br>  -> contract tests<br>  -> merge/release gate |

## 10. 8.9.9 - OpenAPI validation and CI contract-drift gate

| CI check | Failure condition |
| --- | --- |
| Generate spec | Application metadata cannot produce the OpenAPI document. |
| Schema validation | Generated document is invalid against the selected OpenAPI dialect. |
| OperationId uniqueness | Duplicate or missing operationId on public operation. |
| Security coverage | Protected endpoint missing session security, or public endpoint accidentally requires it. |
| Required header coverage | Critical endpoint missing CSRF / Idempotency-Key / Expected-Version / Edit-Lease documentation. |
| Error coverage | Critical endpoint lacks relevant RFC 9457 4xx/5xx responses. |
| Breaking-change diff | Removed path/method, removed required schema/response field, incompatible type/enum/semantics without controlled v2/migration. |
| Drift check | Reviewed API baseline/expected spec differs unexpectedly from generated implementation contract. |

| Merge discipline<br>The generated OpenAPI document is a build artifact, not a manually edited truth. If the generated spec changes, the pull request must show and review the contract change. Unexpected drift blocks merge/release according to the CI policy. |
| --- |


### 10.1 Compatible vs breaking changes

| Change | API version rule |
| --- | --- |
| Add new endpoint | Compatible within v1 if authorization/security remains correct. |
| Add optional response field | Normally compatible within v1; clients must tolerate additive fields. |
| Add optional query parameter | Compatible within v1. |
| Remove/rename field | Breaking -> v2 or controlled migration. |
| Change field type/meaning incompatibly | Breaking -> v2 or controlled migration. |
| Make optional request field required | Breaking. |
| Remove enum value used by clients | Breaking. |
| Tighten validation beyond documented contract | Potential breaking change; explicit review required. |

## 12. 8.9.11 - Documentation quality rules

Every public endpoint has: tag, summary, operationId, auth requirement, parameters, request schema when applicable, success response and relevant error responses.

Descriptions explain business semantics that cannot be inferred from HTTP alone, especially initial publish, direct published-plan mutation, ownership, eligibility and concealment behavior.

Do not duplicate internal implementation details in client-facing descriptions.

Do not describe companyId as a client-controlled tenant selector.

Do not document the removed replacement quota.

Do not document old Draft/Re-Publish behavior superseded by CR-03.

Do not document email mutation through generic Employee PATCH after A8.6-01.

Examples remain synchronized with exact enum values and query/header names.
